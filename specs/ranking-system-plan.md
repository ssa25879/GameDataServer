# 랭킹 시스템 구현 준비

작성일: 2026-10-30

이미지의 과제 조건과 `D:\lecture\랭킹 시스템 구축 요구사항 명세서.docx` v1.0을 기준으로 정리했다. 이번 작업은 요구사항 분석과 구현 준비이며 서버 코드, DB, Unity 화면, 배포 환경은 변경하지 않았다.

## 1. 요구사항과 확정한 정책

이미지의 핵심은 Unity에서 이름·점수를 전송하고, 서버가 DB에 저장한 뒤 상위 10개 점수를 조회하는 것이다. 이미지는 클라이언트 함수와 서버 API를 미리 설계하고 Markdown으로 정리하도록 요구한다.

문서는 여기에 다음 조건을 추가한다.

| 기준 | 완료 조건 |
| --- | --- |
| A1 | Unity에서 이름·점수를 등록하면 서버가 저장된 값과 고유 번호를 201로 반환한다. |
| A2 | 빈 이름이나 음수 점수는 저장하지 않고 400과 거절 이유를 반환한다. |
| A3 | GET `/scores`에서 점수 내림차순 상위 10명과 순위를 반환하고 Unity에서도 표시한다. |
| A4 | 서버를 재시작해도 등록된 점수가 유지된다. |
| A5 | 배포 주소에서 등록·조회가 가능하며 외부 네트워크에서도 같은 랭킹이 보인다. |

사용자가 이번 대화에서 확정한 정책:

- 같은 이름은 한 명으로 취급하고 최고 점수만 유지한다.
- 점수가 같으면 먼저 등록한 사람부터 1위, 2위처럼 서로 다른 순위를 부여한다.

작업 범위는 기존 .NET 서버, SQLite, Unity 클라이언트, 배포 서버다. 새 도구는 도입하지 않는다. 문서의 GitHub push 산출물은 향후 완료 항목이며, 이번 요청은 커밋·푸시·배포 실행 승인이 아니다.

## 3. 구현 시 사용할 설계 초안

아래는 확정 요구사항을 구현하기 위한 제안이다. 문서에 없는 제한을 확정 요구사항으로 취급하지 않는다.

### 데이터와 저장 규칙

기존 몬스터 테이블을 유지하고 같은 DB에 `scores` 테이블을 추가한다.

| 필드 | 제안 형식 | 의미 |
| --- | --- | --- |
| id | INTEGER PRIMARY KEY AUTOINCREMENT | 최초 등록 시 부여하는 고유 번호 |
| name | TEXT NOT NULL UNIQUE | 한 사람을 구분하는 이름 |
| score | INTEGER NOT NULL CHECK(score >= 0) | 해당 이름의 최고 점수 |

- 이름 앞뒤 공백은 제거하고 공백만 입력한 이름도 거절하는 안을 제안한다.
- 정규화한 이름을 정확히 비교하는 안을 제안한다. 대소문자와 유니코드 정규화 정책은 별도 확정되지 않았다.
- 새 이름은 추가하고, 기존 이름은 더 높은 점수일 때만 갱신한다. 같거나 낮은 점수는 기존 최고 점수를 반환한다.
- 최초 등록한 `id`는 최고 점수를 갱신해도 유지한다. 동점 기준인 ‘먼저 등록’은 이 최초 등록 순서로 해석한다.
- 이름별 중복 방지는 DB의 UNIQUE 제약과 원자적 최고 점수 갱신 SQL로 처리한다.
- 정렬은 `score DESC, id ASC`, 반환 개수는 최대 10개로 한다. `rank`는 정렬된 결과에 1부터 부여한다.
- 숫자는 0 이상 정수를 초안으로 사용한다. 32비트 정수를 쓸 경우 최대 2,147,483,647은 구현 자료형의 한계이며 기획상 상한이 아니다.

### API 계약 초안

| 메서드·경로 | 역할 | 응답 |
| --- | --- | --- |
| POST `/scores` | 이름·점수 등록 및 최고 점수 유지 | 유효한 등록은 201, 검증 실패는 400 |
| GET `/scores` | 상위 10명 조회 | 200, `scores` 배열 |

문서의 성공 시 201 요구에 맞춰 기존 이름의 점수 갱신이나 최고 점수 유지도 201로 응답하는 안이다. 반환값의 `score`는 이번 입력값이 아니라 최종 저장된 최고 점수다. 갱신·미갱신을 200으로 구분하려면 원문 요구사항을 먼저 조정해야 한다.

등록 요청:

```http
POST /scores
Content-Type: application/json

{"name":"플레이어1","score":1200}
```

등록 성공 응답 예시 — 201:

```json
{"id":1,"name":"플레이어1","score":1200}
```

이후 같은 이름으로 900을 보내도 저장값과 반환값은 1200이다. 1500을 보내면 같은 id의 최고 점수가 1500으로 변경된다.

검증 실패 응답 예시 — 400:

```json
{"error":"이름을 입력하세요."}
```

```json
{"error":"점수는 0 이상이어야 합니다."}
```

조회 응답 예시 — 200:

```json
{"scores":[{"rank":1,"id":1,"name":"플레이어1","score":1500},{"rank":2,"id":2,"name":"플레이어2","score":1500}]}
```

데이터가 없으면 `{"scores":[]}`를 반환한다. 최상위 객체의 `scores` 배열을 Unity 응답 모델과 일치시킨다. JSON 필드 누락, null, 잘못된 JSON, 소수·범위 초과 입력도 저장 전 거절하고 읽을 수 있는 오류를 반환하도록 설계한다. `score` 누락과 정상 점수 0을 구별해야 한다.

### Unity 함수와 화면 초안

기존 몬스터 실습 화면은 보존하고 랭킹용 스크립트와 화면을 별도로 추가하는 안이다. 실제 씬 수정 전 관련 오브젝트와 연결 상태를 먼저 확인한다.

| 함수 | 역할 |
| --- | --- |
| `OnClickSubmit()` | 이름·점수를 확인하고 등록 요청 후 저장 결과 표시 |
| `SubmitScoreAsync()` | POST `/scores`, 201 확인 및 응답 역직렬화 |
| `OnClickLoadRanking()` | 조회 버튼 이벤트 처리 |
| `FetchScoresAsync()` | GET `/scores`, 200 확인 및 응답 역직렬화 |
| `ShowRanking()` | 순위·이름·점수 목록 표시, 빈 목록 안내 |
| `SetBusy()` | 요청 중 등록·조회 버튼 비활성화, 종료 시 복구 |

화면에는 이름 입력, 점수 입력, 전송 버튼, 상위 10명 조회 버튼, 결과 목록, 상태·오류 문구가 필요하다. 통신은 기존 UnityWebRequest와 async/await 방식을 따른다. 서버 검증은 클라이언트 검증과 별도로 수행한다.

기본 서버 주소는 Inspector에서 지정하고 `/scores`를 붙인다. 로컬 PC와 배포 서버 주소를 구분하며, 폰에서 `localhost`는 개발 PC를 가리키지 않는다. 저장 성공 뒤 조회가 실패하면 ‘저장 성공, 목록 조회 실패’로 구분해 재등록을 유도하지 않는다.

## 4. 구현 순서와 검증

1. **착수 조건 확인**: 기존 서버의 `/hello`, `/monsters` 및 Unity 몬스터 조회가 동작하는지 확인한다. 현재 빌드 성공만으로 이 조건을 충족했다고 보지 않는다.
2. **남은 정책 정리**: 아래 확인 항목을 확정하고 계약·예시를 맞춘다.
3. **서버 구현**: `Program.cs`에 점수 모델, 테이블 초기화, 검증, 등록·조회 API를 추가한다. 기존 몬스터 API와 데이터를 유지한다.
4. **서버 검증**: 별도 임시 DB를 사용해 아래 회귀 조건을 검사한다. 실습용 원본 DB에는 테스트 점수를 넣지 않는다.
5. **Unity 구현**: 랭킹 모델·통신·UI를 연결한다. 해당 폴더의 지침·기존 변경·백업 필요 여부와 쓰기 권한을 확인한 뒤 수행한다.
6. **배포 준비**: 기존 배포의 실제 설정과 SQLite 영속 저장 경로를 확인한다. 재시작 및 재배포 시 DB를 보존하는 방식을 확정한다.
7. **외부 검증과 제출 준비**: A1~A5의 실제 증거, 요청·응답 예시, 배포 주소를 정리한다. 커밋·푸시·배포 실행은 해당 작업 승인 후 진행한다.

| 검증 | 입력·절차 | 기대 결과 |
| --- | --- | --- |
| A1 등록 | 새 이름과 1200 등록 | 201, 고유 번호·이름·1200 반환 |
| 최고 점수 | 같은 이름으로 900, 1200, 1500 순서 등록 | 같은 id, 최종 1500, 중복 행 없음 |
| A2 이름 | 빈 문자열, 공백만, null, 필드 누락 | 400과 이유, DB 변경 없음 |
| A2 점수 | -1, 필드 누락, 소수, 숫자가 아닌 값, 자료형 범위 초과 | 400과 이유, DB 변경 없음 |
| 경계값 | 점수 0, 빈 DB 조회, 10명 미만 조회 | 0 등록 성공, 빈 배열 또는 실제 인원만 반환 |
| A3 랭킹 | 12명 이상과 동점 데이터 등록 | 최대 10명, 점수 내림차순, 동점 최초 등록 순, rank 1~10 |
| 동시 등록 | 같은 이름에 서로 다른 점수 동시 전송 | 한 행만 유지하고 최댓값 저장 |
| A4 영속성 | 등록 후 서버 종료·동일 DB로 재시작 | 점수·id 유지 |
| 기존 회귀 | `/hello`, `/monsters` 조회 | 기존 응답 동작 유지 |
| Unity A1·A3 | 실제 버튼으로 등록·조회 | 201 확인, 목록 표시, 요청 중 중복 클릭 방지 |
| Unity 실패 | 400, 연결 실패, 응답 지연 | 읽을 수 있는 안내, 버튼 복구 |
| A5 외부 | 배포 주소에 등록 후 다른 네트워크의 폰에서 GET `/scores` | 동일 랭킹 확인 |
| 배포 영속성 | 배포 환경 재시작·재배포 전후 비교 | 저장 점수 유지, 이미지 재생성으로 DB 초기화되지 않음 |

문서가 언급한 2-3~2-5 단계마다 이 기준으로 진행 상태를 기록하되, 제공 자료에는 각 단계의 상세 정의가 없어 위 구현 순서를 해당 단계와 임의로 대응시키지 않는다.

## 5. 구현 전 남은 확인

- 이름 최대 길이·허용 문자, 앞뒤 공백 제거와 공백 이름 거절 정책.
- 정수 점수 사용 여부와 점수 상한. 소수가 필요하면 API·DB·Unity 자료형을 함께 조정해야 한다.
- 삭제·수정 기능과 내 순위 표시가 필요한지. 현재 초안에는 별도 기능으로 포함하지 않았다.
- 사용할 배포 환경의 실제 주소, 영속 저장 설정과 비용 조건. 기존 코드의 배포 주소만으로 가동·저장 보존 여부를 단정하지 않는다.

## 6. 이번 준비 작업의 검증 결과

- DOCX 본문·표의 텍스트와 첨부 이미지를 대조했다. DOCX의 시각적 레이아웃 검수는 수행하지 않았다.
- 서버 소스·프로젝트 설정·Dockerfile과 Unity 관련 소스를 읽어 현재 구조를 확인했다.

- 기존 서버 실행, HTTP 요청, DB 내용·재시작, Unity Editor 실행, 배포 주소 접속과 외부 네트워크 검증은 수행하지 않았다. A1~A5는 아직 충족 판정 전이다.
- 이번 산출물은 이 준비 문서 하나다. 커밋·푸시는 수행하지 않았다.
